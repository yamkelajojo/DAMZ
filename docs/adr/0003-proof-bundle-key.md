# ADR-0003: A Proof Bundle is Locked with a Random Per-Order Key Sent Over the Order Chat

**Status**: Accepted

## Context

`DB_LAYOUT_AND_ARCH.md` derived the proof key with HKDF but never defined the input keying material, and `SPEC.md` implied both parties derive it "from the order ID" — which would make the order ID itself the secret. Order IDs are identifiers, seen by the relay, the pinning service, and anyone the parties share them with; they carry no secrecy.

## Decision

Every delivery proof bundle is encrypted with a **fresh random AES-256 key**, generated by the Runner at upload time. The key is sent to the Customer over the encrypted order chat and stored in the order row on both devices (itself protected by SQLCipher). The Admin can decrypt a bundle only when the Customer hands over that one key, which is exactly the evidence a dispute is built on.

## Consequences

- **Considered options**: An order-ID hash (no protection at all); HKDF from the shared Signal session secret (no extra state to store, but the bundle becomes unreadable the moment the session is terminated — precisely when a dispute needs it); a single long-lived platform key (one compromise decrypts every proof ever recorded).
- The photo is never kept on either device — only the CID and the key, so displaying a proof requires a fetch.
- Losing the chat history before the proof is retrieved loses the key; retention therefore keeps the order row (and its key) for 90 days while messages purge at 30.
- The bundle is worthless to anyone who obtains the CID without the key.
